# Development

Use Node.js 22 and npm. The plugin targets Obsidian 1.13.0 or later; the installed API types are pinned so lint and build behaviour do not drift with `latest`.

```bash
npm ci
npm run check
```

`npm run check` runs production-source lint with zero warnings, TypeScript checks, Vitest regressions, and an esbuild production bundle. CI and the tag release workflow run the same check. `npm run dev` watches source changes; `npm run test:watch` watches tests. The bundle is `main.js`; `styles.css` is a maintained source file, not generated by esbuild.

## Test layers

- `tests/engine`: extraction, contextual source maps, schema checks, GraphRAG traversal/templates, Cypher serialization, and safe output writes.
- `tests/settings.test.ts`: migration, independent defaults, ordered writes, and failed-write recovery.
- `tests/ui`: preview/copy flow, stale async jobs, indexed incoming changes, graph-only navigation/history, graph refresh, bounded graph/evidence paging, duplicate-name display, selected provenance, saved questions, retry-save state, and coverage invalidation.
- `tests/integration`: actual sample Markdown through registered commands, duplicate-name caches, grounded prompts, repeated validation/exports, and first use without an index.

Vitest runs in jsdom with a small Obsidian adapter at `tests/mocks/obsidian.ts` and an in-memory vault at `tests/helpers/vault.ts`. These tests exercise plugin logic and DOM interaction; they do not prove compatibility with the running Obsidian host. Keep mocks faithful to the API behaviour needed by each regression, and avoid simulating an unavailable platform as acceptance evidence.

## Native Obsidian check

Copy `examples/sample-vault` to a disposable location. After a successful build, place `main.js`, `styles.css`, and `manifest.json` in its `.obsidian/plugins/kg-forge/` directory. Open that vault and enable Knowledge Forge under Community plugins. Follow [examples/README.md](examples/README.md), including disabling/re-enabling the plugin to check persistence. Reload a plugin by disabling and enabling it after rebuilding; avoid loading an untested build into a personal vault.

Check the developer console for errors, the settings search for plugin settings, keyboard focus in the prompt/evidence controls, and narrow-pane layouts. A browser fixture can inspect rendering and interactions; record it as fixture evidence, separately from native-host evidence.

## Conventions

Production TypeScript uses relative imports and explicit types. Keep engine work independent of views. Use the metadata resolver for note links; full vault paths are canonical identities. Shared folder mapping logic belongs in `engine/FolderMapping.ts`.

All generated writes must use `writeGeneratedFile`; scans use `getSourceFiles` so reports do not feed back into the graph. An ordinary file at an output target is an error, not permission to overwrite it. Settings writes take snapshots and run in order; persistent UI failures must remain visible after reopening a view.

Use scoped `kg-` CSS classes matching the existing views. Catch asynchronous errors and show useful feedback. Add regression coverage for behaviours that could lose data, retrieve unrelated evidence, hang a command, or display stale results. Avoid tests that only repeat implementation details.

Commands register in `src/commands/index.ts`; views register in `src/main.ts` with IDs in `src/constants.ts`. Settings definitions are searchable using the Obsidian 1.13 settings API.

## Releases

A repair branch and passing CI do not publish a plugin release. Before an authorised release:

1. Run `npm ci` and `npm run check` on the intended revision.
2. Complete native sample-vault verification and record any platform/export limits.
3. Update release notes and use `npm version <version>` to update package, manifest, and compatibility versions through the version script. Inspect its commit/tag before pushing.
4. Push the intended tag only when release publication is authorised. The tag workflow checks and uploads `main.js`, `manifest.json`, and `styles.css`.

The current repair does not create a release tag, migrate a user's Cypher store, or install into a personal vault. The durable task record is [docs/DELIVERY.md](docs/DELIVERY.md); no second workflow tracker is required.

## Graph quality experiments

The [frozen eight-task contract and replay instructions](docs/experiments/graph-quality/README.md) cover fact fidelity, actual incoming relationships, graph-only exploration, freshness, bounds and unresolved identities. Preserve failed candidates and independent proofs. A synthetic timing measures the fixed projection model; it does not establish native latency, a global concurrency cap, mobile-host compatibility or superiority over another plugin. Canonical task/recovery state stays in `docs/DELIVERY.md`; experiment results remain subordinate.
